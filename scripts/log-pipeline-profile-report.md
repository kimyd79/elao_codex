# 로그 분석 구간별 성능 측정 — 2026-09-28

측정 대상: `HOM1-W-F11_500MB.log`, 524,951,980 bytes (500.63 MiB), Apache 형식.
원본 664,076줄 중 NUL이 포함된 1줄을 제외하고 664,075줄을 적재했다.
저장 모드는 `dynamic`이다.

## 결론

가장 느린 단계는 Validating: **523.279초**. 측정 구간 합계 612.682초의 **85.41%**다.
검증 내부에서 가장 느린 연산은 `loganalyzerapi/parsers.py`의 `shlex.split(line)`이다.
파일 전체에 고르게 분포한 2,000줄을 3회 측정한 결과, 줄별 검증 함수 시간의 **95.88%**가
이 함수에 사용됐다. 날짜 해석은 **3.21%**, 기타 검사는 **0.91%**였다.
이 비율은 파일 읽기·쓰기까지 포함한 전체 Validating 시간의 직접 분해값은 아니다.

## 방법과 범위

- 실제 검증 함수와 실제 Apache 파서, 실제 CSV COPY 함수를 사용했다.
- 최초 전체 파일 측정은 검증까지 완료했으나, 측정 도구가 오류 줄 처리를 지원하지 않아
  검증 이후 중단됐다. Reading/Validating 시간은 해당 실행의 출력에서 보존했다.
- 후속 구간은 기존에 기록된 오류 줄의 위치와 원문 일치를 확인하여 같은 정상 입력을
  재구성한 뒤 2회 측정했다. 재구성 비용 5.24~5.78초는 운영 단계 시간에 더하지 않았다.
- 데이터 적재는 기존 테이블의 구조와 인덱스를 복제한 별도 일반 PostgreSQL 테이블에서
  수행하고 롤백했다. 원본 분석 데이터는 수정하지 않았다.
- 따라서 612.682초는 따로 측정한 구간의 합이며, 단일 연속 요청의 실측 총시간은 아니다.
- 운영 테이블의 기존 데이터 규모, 동시 부하, 잠금 대기, 커밋 및 HTTP 비용은 재현하지 않았다.
  압축 해제와 V2 복사는 이번 파일/설정에 해당하지 않는다.
- 참고로 같은 파일의 이전 실제 분석 작업은 612.031초가 걸렸다.

## 개선 우선순위

1. Apache 형식 검증에서 범용 셸 구문 파서인 `shlex.split` 비용을 줄이는 것이 최우선이다.
   따옴표·이스케이프·필드 수 검사 등 기존 의미를 보존하는 형식 전용 파서가 필요하다.
2. 다음 후보는 CSV 생성과 중복 읽기다. CSV 쓰기에 약 28.8초, 파서의 두 번 읽기에 약 14.3초가 든다.
3. 날짜 해석이나 오류 내역 저장은 현재 파일의 주된 병목이 아니다.

수정한 것은 측정 도구와 결과 파일이며, 운영 파서의 동작은 변경하지 않았다.
원시 수치: `log-pipeline-profile.json`. 재사용 측정 도구: `profile_log_pipeline.py`.
