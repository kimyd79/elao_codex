# ELAO 액세스 로그 파싱 및 저장 개선 계획

## 1. 문서 목적

이 문서는 현재 ELAO의 액세스 로그 업로드, 파싱, 임시 CSV 생성 및 PostgreSQL 저장 과정을 안전하고 점진적으로 개선하기 위한 작업 목록이다.

각 항목은 가급적 다음 조건을 만족하는 하나의 작업 단위로 나눈다.

- 한 번의 구현, 테스트, 검토 및 커밋으로 관리할 수 있다.
- 기존 동작에 미치는 영향과 롤백 범위를 작게 유지한다.
- 앞 단계가 검증된 후 다음 단계로 진행한다.
- 대규모 구조 변경은 신규 구조를 병행 운영한 뒤 전환한다.

## 2. 작업 관리 규칙

각 작업을 시작할 때 아래 상태와 실행 정보를 갱신한다.

- 상태: `대기`, `진행 중`, `검증 중`, `완료`, `보류`
- 담당자:
- 시작일:
- 완료일:
- 관련 커밋 또는 PR:
- 테스트 결과 및 증빙:
- 발견된 추가 과제:

완료 판정은 코드 수정만으로 하지 않는다. 각 항목의 테스트와 결과 확인 조건을 모두 만족해야 `완료`로 변경한다.

## 3. 공통 기준 데이터 준비

개선 작업 전후의 결과를 비교할 수 있도록 아래 파일을 고정된 테스트 데이터로 관리한다. 실제 개인정보, 인증 토큰, 세션 값은 제거한다.

| 데이터 | 권장 크기 | 확인 목적 |
|---|---:|---|
| Apache 정상 로그 | 100~1,000행 | 기본 필드 파싱 |
| Nginx 정상 로그 | 100~1,000행 | 기본 필드 및 request time 파싱 |
| IIS-W3C 정상 로그 | 100~1,000행 | 날짜, 시간 및 URI 조합 |
| 비정상 행 혼합 로그 | 정상 95행 + 비정상 5행 | 실패 행 감지와 보존 |
| UTF-8 이외 인코딩 로그 | 100행 | 인코딩 처리 |
| 긴 URI/User-Agent 로그 | 10행 | 필드 길이 초과 처리 |
| GZ 압축 로그 | 100~1,000행 | Gzip 처리 |
| ZIP 압축 로그 | 1개 및 복수 내부 파일 | ZIP 검증과 처리 정책 |
| 중간 규모 로그 | 10만 행 이상 | 처리시간과 메모리 비교 |

각 기준 데이터에는 기대 결과를 함께 기록한다.

```text
파일명
원본 행 수
정상 파싱 예상 행 수
실패 예상 행 번호와 사유
최초/최종 로그 시각
상태 코드별 건수
응답 바이트 합계
```

# 우선순위 1: 즉시 적용 가능한 안전성 보완

## 작업 1. 임시 파일 정리 보장

- 우선순위: P0
- 상태: 완료
- 예상 변경 범위: 작음
- 선행조건: 없음

### 1. 개선 필요항목 정의

파싱 중 생성되는 `*_0.csv`, `*_X-Forwarded-For`, `*_decompressed` 파일이 성공 또는 실패 후에도 남을 수 있다. 반복 분석 시 디스크가 증가하고 과거 임시 파일과 충돌할 위험이 있다.

### 2. 개선 방법 정의

- 임시 파일 경로를 작업별 임시 디렉터리로 모은다.
- 생성된 임시 파일 목록을 추적한다.
- 파싱과 COPY 처리를 `try/finally`로 감싸 성공 및 실패 시 모두 정리한다.
- 원본 업로드 파일은 삭제하지 않는다.
- 이번 작업에서는 파싱 방식이나 DB 스키마를 변경하지 않는다.

### 3. 테스트 방법 및 데이터 확인

- 정상 Apache 로그를 분석하고 임시 파일이 남지 않는지 확인한다.
- COPY 직전에 의도적으로 오류를 발생시켜 실패 후에도 임시 파일이 제거되는지 확인한다.
- 원본 업로드 파일은 그대로 존재하는지 확인한다.

### 4. 결과 확인

- 정상 및 실패 처리 후 작업 디렉터리에 임시 파일이 0개다.
- 원본 로그와 기존 DB 결과는 변경 전과 동일하다.
- 서버 로그에 임시 파일 정리 실패가 기록되지 않는다.

### 롤백 기준

원본 파일이 삭제되거나 Windows에서 파일 잠금 오류가 반복되면 해당 변경을 롤백한다.

## 작업 2. 대용량 분할 호출 오류와 마지막 행 누락 수정

- 우선순위: P0
- 상태: 완료
- 예상 변경 범위: 작음
- 선행조건: 공통 기준 데이터 준비

### 1. 개선 필요항목 정의

대용량 처리 경로에서 `parse_log_div()` 호출 시 `diff_hour` 인자가 누락돼 실행 오류가 발생할 수 있다. 행 수를 균등 분할할 때 나머지 행이 마지막 청크에서 빠질 가능성도 있다.

### 2. 개선 방법 정의

- 모든 `parse_log_div()` 호출의 인자 개수와 순서를 통일한다.
- 마지막 청크가 전체 나머지 행을 포함하도록 계산한다.
- 파일 크기 기준을 임의로 낮출 수 있는 테스트용 설정을 추가해 거대한 파일 없이 분할 경로를 검증한다.
- 이 단계에서는 기존 `skiprows` 방식은 유지한다.

### 3. 테스트 방법 및 데이터 확인

- 101행 파일을 4개 청크로 나누어 처리한다.
- `diff_hour=0`, 양수, 음수 조건을 각각 실행한다.
- 첫 행과 마지막 행의 저장 여부를 확인한다.

### 4. 결과 확인

- 인자 누락 예외가 발생하지 않는다.
- 저장 행 수가 원본의 파싱 가능 행 수와 일치한다.
- 각 원본 행이 한 번만 저장된다.
- 시간 보정 결과가 단일 파일 처리 결과와 동일하다.

## 작업 3. 파싱 및 저장 건수 기록

- 우선순위: P0
- 상태: 완료
- 예상 변경 범위: 작음~중간
- 선행조건: 공통 기준 데이터 준비

### 1. 개선 필요항목 정의

현재 API 성공 응답만으로는 원본 행 수, 파싱 성공 행 수, 제외 행 수 및 DB 저장 행 수를 알 수 없다. 일부 행이 누락되어도 성공으로 인식될 수 있다.

### 2. 개선 방법 정의

- 우선 DB 스키마를 변경하지 않고 처리 결과를 구조화된 서버 로그와 API 응답에 추가한다.
- 최소한 `source_count`, `parsed_count`, `rejected_count`, `stored_count`를 계산한다.
- 아래 불변 조건을 검사한다.

```text
source_count = parsed_count + rejected_count
stored_count = parsed_count
```

- 조건이 맞지 않으면 성공 응답을 반환하지 않는다.

### 3. 테스트 방법 및 데이터 확인

- 정상 로그와 비정상 5행이 포함된 로그를 각각 분석한다.
- API 응답, 서버 로그 및 실제 DB `COUNT(*)`를 비교한다.
- 빈 파일과 마지막 줄에 개행이 없는 파일도 확인한다.

### 4. 결과 확인

- 모든 테스트 파일에서 네 가지 건수를 확인할 수 있다.
- API의 `stored_count`와 DB 조회 건수가 일치한다.
- 건수 불일치 시 성공으로 표시되지 않는다.

## 작업 4. 실패 행의 조용한 누락 방지

- 우선순위: P0
- 상태: 완료
- 예상 변경 범위: 중간
- 선행조건: 작업 3

### 1. 개선 필요항목 정의

`error_bad_lines=False`와 `dropna()` 때문에 포맷이 맞지 않는 행이 이유 없이 제거될 수 있다. 장애 또는 보안 분석에서 중요한 로그가 누락될 위험이 있다.

### 2. 개선 방법 정의

- pandas가 비정상 행을 조용히 건너뛰지 않도록 파싱 오류를 수집한다.
- 1차 단계에서는 실패 행을 작업별 reject CSV 또는 JSONL 파일로 저장한다.
- 실패 정보에 `logfile_id`, 원본 행 번호, 원문, 오류 코드를 포함한다.
- 실패율 정책을 설정값으로 둔다. 초기 권장값은 실패 행이 하나라도 있으면 `PARTIAL`로 취급하는 것이다.
- reject 파일에 인증 헤더, 쿠키 등 민감정보가 포함될 수 있음을 문서화하고 접근 범위를 제한한다.

### 3. 테스트 방법 및 데이터 확인

- 정상 95행과 의도적으로 손상시킨 5행을 처리한다.
- 손상 유형별로 필드 부족, 숫자 변환 실패, 잘못된 날짜를 포함한다.
- reject 파일의 행 번호와 원문이 기준 데이터와 일치하는지 확인한다.

### 4. 결과 확인

- 성공 95행과 실패 5행이 정확히 구분된다.
- 실패 사유를 사용자가 확인할 수 있다.
- 실패 행이 있으면 완전 성공으로 표시되지 않는다.
- 정상 로그 처리 결과에는 변화가 없다.

# 우선순위 2: 실패 복구와 압축 처리 보완

## 작업 5. 파일 단위 처리 상태 관리

- 우선순위: P1
- 상태: 완료
- 예상 변경 범위: 중간
- 선행조건: 작업 3, 작업 4

### 1. 개선 필요항목 정의

현재는 업로드, 파싱 및 저장 진행 상태를 구분하지 못한다. 실패 후 일부 데이터가 남았는지, 재처리해도 되는지 판단하기 어렵다.

### 2. 개선 방법 정의

- 별도의 분석 작업 모델을 추가한다.
- 상태는 `UPLOADED`, `PARSING`, `LOADING`, `VALIDATING`, `COMPLETED`, `PARTIAL`, `FAILED`로 관리한다.
- 처리 건수, 오류 요약, 시작·종료 시각을 작업 레코드에 기록한다.
- 우선 기존 동기 API를 유지하고 상태 기록만 추가한다.

### 3. 테스트 방법 및 데이터 확인

- 정상, 파싱 실패, DB 저장 실패를 각각 발생시킨다.
- 상태 변경 순서와 종료 상태를 확인한다.
- 서버 재시작 후에도 마지막 상태가 유지되는지 확인한다.

### 4. 결과 확인

- 모든 파일의 현재 처리 상태와 처리 건수를 조회할 수 있다.
- 실패 단계와 오류 원인이 구분된다.
- `COMPLETED`는 검증까지 끝난 작업에만 설정된다.

## 작업 6. 부분 저장 방지와 안전한 재처리

- 우선순위: P1
- 상태: 완료
- 예상 변경 범위: 중간
- 선행조건: 작업 5

### 1. 개선 필요항목 정의

여러 CSV 또는 청크 중 일부만 DB 저장에 성공하면 부분 데이터가 남는다. 이후 재실행이 막히거나 중복 데이터가 저장될 수 있다.

### 2. 개선 방법 정의

- 우선 파일 한 개의 저장 범위를 `transaction.atomic()`으로 보호한다.
- 실패 시 해당 `logfile_id`에 이번 작업이 저장한 데이터를 제거하거나 전체 롤백한다.
- 재처리 전에 기존 작업 상태를 검사한다.
- 동시 분석 요청을 막기 위해 동일 `logfile_id` 작업 잠금 정책을 추가한다.
- 장기 트랜잭션 문제가 확인되면 후속 작업에서 staging 테이블 방식으로 교체한다.

### 3. 테스트 방법 및 데이터 확인

- 여러 청크 중 두 번째 청크 COPY에서 강제로 실패시킨다.
- 실패 후 해당 파일의 저장 행 수를 확인한다.
- 동일 파일을 즉시 재처리하고 중복 여부를 확인한다.
- 동시에 두 번 분석 요청을 보낸다.

### 4. 결과 확인

- 실패 후 부분 데이터가 조회되지 않는다.
- 재처리 후 정확한 행 수만 한 번 저장된다.
- 동일 파일의 동시 처리가 하나만 실행된다.

## 작업 7. 원본 파일 해시와 중복 판별

- 우선순위: P1
- 상태: 대기
- 예상 변경 범위: 작음~중간
- 선행조건: 작업 5

### 1. 개선 필요항목 정의

동일 파일을 이름만 바꿔 업로드하거나 포맷 설정만 바꿔 재처리하는 경우를 구분할 수 없다.

### 2. 개선 방법 정의

- 업로드 파일을 스트리밍하면서 SHA-256을 계산해 `source_hash`로 저장한다.
- `source_hash`, 포맷 버전, 시간 보정 값 및 파서 버전을 분석 작업에 기록한다.
- 동일 조합의 완료 작업이 있으면 사용자에게 중복 여부를 알린다.
- 초기에는 중복 업로드를 강제 차단하지 않고 경고와 재사용 선택지를 제공한다.

### 3. 테스트 방법 및 데이터 확인

- 같은 파일, 이름만 바꾼 같은 파일, 한 줄이 변경된 파일을 업로드한다.
- 같은 파일에 다른 포맷과 시간 보정을 적용한다.

### 4. 결과 확인

- 내용이 같으면 파일명이 달라도 같은 해시가 생성된다.
- 내용이 다르면 다른 해시가 생성된다.
- 설정이 다른 재분석은 별도 작업으로 구분된다.

## 작업 8. GZ 압축 로그 처리 정상화

- 우선순위: P1
- 상태: 대기
- 예상 변경 범위: 작음~중간
- 선행조건: 작업 1, 작업 3

### 1. 개선 필요항목 정의

현재는 압축 해제 예상 크기가 기준보다 큰 경우에만 압축을 해제한다. 작은 GZ 파일이 압축 상태로 텍스트 파서에 전달될 수 있다.

### 2. 개선 방법 정의

- 파일 크기와 무관하게 Gzip signature를 확인한다.
- Gzip 스트림을 텍스트 스트림으로 열어 파서에 전달한다.
- 압축 해제 최대 크기와 압축률 제한을 설정한다.
- 이번 작업에서는 ZIP 처리를 변경하지 않는다.

### 3. 테스트 방법 및 데이터 확인

- 같은 원본의 일반 파일과 GZ 파일을 각각 분석한다.
- 손상된 GZ와 비정상적으로 큰 압축 해제 크기를 가진 파일을 테스트한다.

### 4. 결과 확인

- 일반 파일과 GZ 파일의 파싱 결과 및 건수가 동일하다.
- 손상되거나 제한을 초과한 파일은 명확한 사유로 거부된다.
- 전체 압축 해제 임시 파일이 남지 않는다.

## 작업 9. ZIP 압축 로그 처리 정책 적용

- 우선순위: P1
- 상태: 대기
- 예상 변경 범위: 중간
- 선행조건: 작업 1, 작업 3, 작업 8

### 1. 개선 필요항목 정의

ZIP 내부 파일이 여러 개일 때 처리 기준이 없고, 첫 파일과 마지막 파일을 혼용해 크기를 판단한다. 경로 순회와 ZIP bomb 방어도 필요하다.

### 2. 개선 방법 정의

- 내부 파일 개수, 파일명, 확장자, 각 파일 크기 및 합산 크기를 검증한다.
- `../` 또는 절대 경로가 포함된 항목을 거부한다.
- 1차 구현에서는 로그 파일 하나만 포함된 ZIP을 허용한다.
- 다중 파일 ZIP 지원은 별도 후속 작업으로 남긴다.
- `extractall()` 대신 검증된 단일 항목 스트림을 처리한다.

### 3. 테스트 방법 및 데이터 확인

- 단일 로그 ZIP, 다중 로그 ZIP, 빈 ZIP, 디렉터리 포함 ZIP을 테스트한다.
- 경로 순회 항목 및 허용 크기를 초과하는 ZIP을 테스트한다.

### 4. 결과 확인

- 단일 로그 ZIP은 일반 파일과 동일하게 처리된다.
- 지원하지 않는 ZIP은 구체적인 사유로 안전하게 거부된다.
- 업로드 디렉터리 밖으로 파일이 생성되지 않는다.

# 우선순위 3: 성능과 파싱 정확성 개선

## 작업 10. 순차 청크 파싱 도입

- 우선순위: P2
- 상태: 대기
- 예상 변경 범위: 중간
- 선행조건: 작업 3, 작업 4, 작업 6

### 1. 개선 필요항목 정의

현재 대용량 처리는 `skiprows`로 앞부분을 반복해서 훑고, 한 청크도 원문과 파싱 목적으로 두 번 읽는다. 파일이 클수록 디스크 I/O와 처리시간이 증가한다.

### 2. 개선 방법 정의

- 우선 Apache 한 종류에만 `chunksize` 기반 순차 읽기를 적용한다.
- 청크 크기는 설정값으로 두고 초기값은 10만 행으로 한다.
- 원문과 파싱 필드를 한 번의 순회에서 생성한다.
- 기존 파서는 fallback으로 유지해 결과를 비교한다.
- Apache 검증 후 Nginx, IIS 순서로 적용 범위를 확장한다.

### 3. 테스트 방법 및 데이터 확인

- 동일한 10만 행 이상 파일을 기존 방식과 신규 방식으로 처리한다.
- 행별 주요 필드, 전체 건수, 상태별 집계 및 최초/최종 시각을 비교한다.
- 처리시간, 최대 메모리, 임시 디스크 사용량을 측정한다.

### 4. 결과 확인

- 신규 방식의 데이터 결과가 기존 정상 결과와 일치한다.
- 파일을 처음부터 끝까지 한 번만 순차적으로 읽는다.
- 최대 메모리가 청크 크기에 비례하며 파일 전체 크기에 비례하지 않는다.
- 성능 측정 결과를 문서에 기록한다.

## 작업 11. 임시 CSV 없는 PostgreSQL COPY 스트림

- 우선순위: P2
- 상태: 대기
- 예상 변경 범위: 중간
- 선행조건: 작업 10

### 1. 개선 필요항목 정의

파싱 결과를 임시 CSV로 디스크에 쓴 뒤 다시 읽어 DB에 저장하므로 추가 쓰기와 읽기가 발생한다.

### 2. 개선 방법 정의

- 한 개 파서와 한 개 로그 형식부터 메모리 버퍼 또는 스트림을 PostgreSQL COPY에 직접 전달한다.
- 청크 단위로 저장하되 작업 상태와 저장 건수를 함께 갱신한다.
- 메모리 버퍼 최대 크기를 제한한다.
- 기존 CSV COPY 방식을 fallback으로 유지한다.

### 3. 테스트 방법 및 데이터 확인

- 기존 CSV 방식과 스트림 방식의 저장 결과를 비교한다.
- DB 저장 중 실패, 연결 종료 및 서버 재시작 상황을 테스트한다.
- 처리시간과 임시 디스크 사용량을 비교한다.

### 4. 결과 확인

- 저장 행과 컬럼 값이 기존 정상 결과와 동일하다.
- 중간 CSV 파일이 생성되지 않는다.
- 저장 실패 시 부분 데이터 처리 정책이 작업 6의 기준을 만족한다.

## 작업 12. 포맷별 파서 클래스 분리

- 우선순위: P2
- 상태: 대기
- 예상 변경 범위: 중간
- 선행조건: 작업 4, 작업 10

### 1. 개선 필요항목 정의

Apache, Nginx, IIS 및 애플리케이션 로그 처리가 하나의 큰 ViewSet에 섞여 있어 수정 영향 범위가 크고 포맷별 테스트가 어렵다.

### 2. 개선 방법 정의

- 먼저 현재 로직을 동작 변경 없이 서비스와 파서 모듈로 이동한다.
- 공통 인터페이스를 정의한다.

```python
validate_format(format_string)
parse_chunk(lines)
normalize(parsed_rows)
```

- Apache 파서를 먼저 분리하고 테스트한 뒤 Nginx, IIS, App을 각각 별도 작업으로 분리한다.
- ViewSet은 입력 검증과 작업 실행만 담당한다.

### 3. 테스트 방법 및 데이터 확인

- 분리 전후 동일 기준 로그의 모든 저장 컬럼을 비교한다.
- 포맷별 단위 테스트를 독립 실행한다.
- 알 수 없는 `format_kind`가 명확하게 거부되는지 확인한다.

### 4. 결과 확인

- ViewSet에서 pandas 기반 파싱 구현이 제거된다.
- 포맷별 테스트가 다른 포맷에 의존하지 않는다.
- 리팩터링 전후 결과가 동일하다.

## 작업 13. 로그 포맷 등록 시 샘플 검증

- 우선순위: P2
- 상태: 대기
- 예상 변경 범위: 중간
- 선행조건: 작업 12

### 1. 개선 필요항목 정의

현재 포맷 오류는 실제 파일 분석 단계에서야 발견된다. 단순 공백 분리 방식은 인용부호와 선택 필드에 취약하다.

### 2. 개선 방법 정의

- 포맷 등록 화면에 샘플 로그 1~10행 검증 기능을 추가한다.
- 파서가 인식한 IP, 시각, 요청, 상태, 바이트 및 응답시간을 미리 보여준다.
- 필수 필드 누락, 필드 수 불일치 및 날짜 변환 오류를 저장 전에 알린다.
- 기존 포맷은 비활성화하지 않고 검증 상태를 별도로 표시한다.

### 3. 테스트 방법 및 데이터 확인

- 포맷별 정상 샘플과 필드가 하나씩 누락된 샘플을 사용한다.
- User-Agent, Referer 및 요청 URI에 공백과 따옴표가 포함된 데이터를 확인한다.

### 4. 결과 확인

- 잘못된 포맷을 대용량 분석 전에 발견할 수 있다.
- 사용자가 실제 추출값을 확인하고 포맷을 저장할 수 있다.
- 기존 포맷의 호환성 상태를 식별할 수 있다.

# 우선순위 4: 데이터 모델과 조회 구조 개선

## 작업 14. 데이터 타입과 길이 정책 보완

- 우선순위: P3
- 상태: 대기
- 예상 변경 범위: 중간~큼
- 선행조건: 작업 12, 작업 13

### 1. 개선 필요항목 정의

날짜, 상태 코드, UUID가 문자열로 저장되고 원문 및 요청 필드 길이가 제한돼 있다. 긴 URI나 User-Agent 한 행 때문에 COPY 전체가 실패할 수 있으며 시간대도 보존되지 않는다.

### 2. 개선 방법 정의

- 기존 동적 테이블을 즉시 변경하지 않고 신규 V2 저장 모델을 만든다.
- 권장 타입은 다음과 같다.

| 필드 | 권장 타입 |
|---|---|
| `occurred_at` | `timestamptz` |
| `status` | `smallint` |
| `bytes_sent` | `bigint` |
| `duration_us` | `bigint`, null 허용 |
| `client_ip` | PostgreSQL `inet` 또는 검증된 문자열 |
| `logfile_id` | UUID 외래키 |
| `raw_line` | `text` |
| URI, Referer, User-Agent | `text` |

- 응답시간이 없으면 인접 행으로 추정하지 않고 `NULL`로 저장한다.
- 기존 테이블과 V2에 병행 저장해 비교한다.

### 3. 테스트 방법 및 데이터 확인

- 시간대가 다른 로그와 긴 URI/User-Agent 로그를 처리한다.
- 기존 결과와 V2 결과의 행 수 및 주요 통계를 비교한다.
- 응답시간 미포함 로그가 `NULL`로 저장되는지 확인한다.

### 4. 결과 확인

- 긴 문자열 때문에 전체 적재가 실패하지 않는다.
- 시간대가 UTC 기준으로 정확히 정렬된다.
- 실제 응답시간과 미측정 값이 구분된다.
- 기존 화면 통계와 차이가 있다면 원인을 설명할 수 있다.

## 작업 15. 조회 인덱스 적용

- 우선순위: P3
- 상태: 대기
- 예상 변경 범위: 작음~중간
- 선행조건: 작업 14

### 1. 개선 필요항목 정의

기간, 로그파일, 상태 코드 및 응답시간 조회에 적절한 인덱스가 없어 데이터 증가 시 전체 테이블 스캔이 발생할 수 있다.

### 2. 개선 방법 정의

- 실제 화면의 주요 쿼리를 수집하고 `EXPLAIN ANALYZE` 기준으로 인덱스를 선정한다.
- 우선 `(logfile_id, occurred_at)`, `(project_id, occurred_at)` 복합 인덱스를 검토한다.
- 상태 및 응답시간 인덱스는 선택도와 실제 사용 빈도를 확인한 후 추가한다.
- 원문 부분 문자열 검색은 `pg_trgm` 도입을 별도 판단한다.

### 3. 테스트 방법 및 데이터 확인

- 충분한 건수의 V2 데이터를 준비한다.
- 인덱스 전후 동일 조회의 실행 계획, 실행시간 및 DB 크기를 비교한다.
- 로그 적재 속도 저하도 함께 측정한다.

### 4. 결과 확인

- 주요 기간 조회가 의도한 인덱스를 사용한다.
- 조회시간 개선 수치가 기록된다.
- 적재 성능과 저장공간 증가가 허용 범위에 있다.

## 작업 16. 동적 테이블 제거 가능성 검증

- 우선순위: P4
- 상태: 대기
- 예상 변경 범위: 큼, 조사 및 검증부터 수행
- 선행조건: 작업 14, 작업 15

### 1. 개선 필요항목 정의

프로젝트마다 동적 테이블을 생성하면 스키마, 인덱스, 외래키 및 마이그레이션 관리가 복잡해지고 `django-dynamic-model`에 계속 의존하게 된다.

### 2. 개선 방법 정의

- 바로 제거하지 않고 V2 단일 테이블의 병행 운영 결과를 먼저 검증한다.
- 데이터 규모에 따라 월 단위 또는 프로젝트 해시 PostgreSQL 파티셔닝을 비교한다.
- 기존 동적 테이블 조회 API와 V2 API를 일정 기간 병행한다.
- 건수, 통계, 조회속도 및 삭제 성능이 검증된 후 전환 계획을 별도 작성한다.

### 3. 테스트 방법 및 데이터 확인

- 동일 데이터를 기존 동적 테이블과 V2 테이블에 저장한다.
- 기간 검색, 상태별 집계, URI 통계, 프로젝트 삭제 및 백업·복구를 비교한다.
- 여러 프로젝트를 동시에 처리해 테이블 증가와 단일 테이블 증가를 비교한다.

### 4. 결과 확인

- 기능 및 통계 결과가 허용 범위에서 일치한다.
- V2의 조회·삭제·백업 성능이 운영 기준을 만족한다.
- 기존 동적 테이블을 제거하기 전 복구 및 롤백 절차가 준비된다.

# 4. 권장 실행 순서

아래 순서를 기본으로 하되, 각 작업은 별도 커밋 또는 PR로 관리한다.

```text
기준 데이터 준비
  → 작업 1 임시 파일 정리
  → 작업 2 대용량 호출/나머지 수정
  → 작업 3 처리 건수 기록
  → 작업 4 실패 행 보존
  → 작업 5 처리 상태 관리
  → 작업 6 부분 저장/재처리 보완
  → 작업 7 파일 해시
  → 작업 8 GZ 처리
  → 작업 9 ZIP 처리
  → 작업 10 순차 청크 파싱
  → 작업 11 COPY 스트림
  → 작업 12 포맷별 파서 분리
  → 작업 13 포맷 사전 검증
  → 작업 14 V2 데이터 타입
  → 작업 15 조회 인덱스
  → 작업 16 동적 테이블 제거 검증
```

## 5. 작업별 커밋 원칙

- 한 커밋에 여러 작업 번호를 섞지 않는다.
- 리팩터링과 기능 변경을 가능하면 별도 커밋으로 나눈다.
- DB 스키마 변경에는 migration과 원복 절차를 포함한다.
- 테스트 데이터의 개인정보와 인증정보를 제거한다.
- 성능 개선은 변경 전후 측정값을 남긴다.
- 완료한 작업은 상태, 커밋 ID, 테스트 결과를 이 문서에 기록한다.

## 6. 전체 완료 기준

- 원본 행, 성공 행, 실패 행 및 저장 행 수를 확인할 수 있다.
- 실패 행이 사유 없이 버려지지 않는다.
