# ELAO 기술 스택 현대화 및 기능 개선 통합 로드맵

## 1. 목적

이 문서는 ELAO의 기술 스택 현대화와 액세스 로그 파싱·저장 기능 개선을 안전한 순서로 실행하기 위한 최상위 작업 계획서다.

핵심 원칙은 다음과 같다.

1. 현재 동작을 테스트와 기준 데이터로 먼저 고정한다.
2. 데이터 유실과 부분 저장처럼 결과 신뢰성을 해치는 위험을 먼저 줄인다.
3. 큰 파서 리팩터링 전에 백엔드와 프런트엔드 기술 스택을 단계적으로 현대화한다.
4. 현대화된 기반에서 성능, 파서 구조 및 저장 모델을 개선한다.
5. 동적 테이블 제거는 신규 구조의 병행 검증이 완료된 후 결정한다.

상세 참고 문서는 다음과 같다.

- 기능 개선 상세: [ACCESS_LOG_PARSING_IMPROVEMENT_PLAN.md](ACCESS_LOG_PARSING_IMPROVEMENT_PLAN.md)
- 기술 스택 상세: [STACK_MODERNIZATION_PLAN.md](STACK_MODERNIZATION_PLAN.md)

이 문서를 실제 작업 순서와 상태를 관리하는 기준 문서로 사용하고, 위 두 문서는 구현 시 세부사항을 확인하는 참고 문서로 사용한다.

## 2. 작업 관리 원칙

### 작업 단위

- 아래 작업 한 개를 원칙적으로 커밋 또는 PR 한 개로 관리한다.
- 작업 안에서도 의존성 업그레이드와 기능 변경은 별도 커밋으로 분리할 수 있다.
- 다음 작업은 현재 작업의 테스트 및 결과 확인이 완료된 후 시작한다.
- DB 스키마 변경에는 migration, 백업 및 원복 절차가 반드시 포함돼야 한다.

### 상태 값

각 작업의 `상태`를 다음 중 하나로 변경한다.

- `대기`
- `진행 중`
- `검증 중`
- `완료`
- `보류`

각 작업을 진행할 때 아래 항목도 기록한다.

```text
담당자:
시작일:
완료일:
관련 커밋/PR:
테스트 결과:
백업 위치:
발견된 추가 과제:
```

### 공통 완료 조건

- 실행 및 원복 명령이 문서화돼 있다.
- 자동 테스트와 수동 확인 결과가 남아 있다.
- `.env`, 원본 운영 로그, DB 덤프 및 개인정보가 Git에 포함되지 않는다.
- 기존 정상 샘플의 주요 통계 결과가 의도 없이 변경되지 않는다.
- 변경 전 백업으로 복구할 수 있다.

# 1단계: 현재 동작과 데이터 신뢰성 고정

## 작업 1. 기준 데이터와 기대 결과 명세 준비

- 상태: 완료
- 선행조건: 없음
- 관련 상세 작업: 기능 개선 계획의 공통 기준 데이터 준비

```text
담당자: Codex
시작일: 2026-08-11
완료일: 2026-08-11
관련 커밋/PR: 커밋 전
테스트 결과: JSON 문법, 물리/주석/데이터 행 수 불변조건, 상태별 건수,
             바이트 및 응답시간 합계, 민감정보 패턴 검사 통과
백업 위치: Git 작업 트리(커밋 전)
발견된 추가 과제: 실제 파서 실행 결과 비교는 작업 2의 자동 회귀 테스트에서 수행
```

### 1. 개선 필요항목 정의

현재는 파서 수정이나 버전 업그레이드 전후 결과를 비교할 고정된 기준 로그와 기대 결과가 없다. 결과가 달라졌을 때 개선인지 회귀 오류인지 판단하기 어렵다.

### 2. 개선 방법 정의

- Apache, Nginx, IIS-W3C, App 로그의 비식별 샘플을 준비한다.
- 정상, 비정상, 긴 문자열, 다른 인코딩, GZ 및 ZIP 샘플을 분리한다.
- 각 파일의 원본 행 수, 정상 예상 행 수, 실패 예상 행, 최초·최종 시각, 상태별 건수를 명세 파일로 관리한다.
- 현재 정상 실행 결과를 기준 결과로 추출한다.
- 샘플과 기대 결과만 추가하고 운영 코드는 변경하지 않는다.

### 3. 테스트 방법 및 데이터 확인

- 샘플에 개인정보, 토큰, 쿠키 및 내부 주소가 남아 있지 않은지 확인한다.
- 기대 행 수를 별도 명령으로 다시 계산한다.
- 현재 애플리케이션에서 샘플을 수동 분석해 기준 결과와 비교한다.

### 4. 결과 확인

- 최소 3종 웹 로그와 비정상 로그의 기준 데이터가 존재한다.
- 모든 샘플에 기대 결과가 기록돼 있다.
- 이후 작업에서 동일 샘플을 반복 사용할 수 있다.

### 롤백 및 중단 기준

비식별화 여부를 확인할 수 없는 실제 운영 로그는 저장소에 추가하지 않는다.

## 작업 2. 핵심 회귀 테스트 구축

- 상태: 완료
- 선행조건: 작업 1
- 관련 상세 작업: 기술 스택 계획 1단계

```text
담당자: Codex
시작일: 2026-08-11
완료일: 2026-08-11
관련 커밋/PR: 커밋 전
테스트 결과: PostgreSQL 격리 테스트 DB에서 9개 테스트 통과

발견된 추가 과제: 분석 요청의 업로드 FieldFile 핸들이 요청 종료까지 열려 있음
                   중복 router 등록으로 reverse URL 이름이 비정상적임
                   실행 중 서버가 Windows 로그 파일을 독점 잠금함
```

### 1. 개선 필요항목 정의

현재 자동 테스트가 거의 없어 기능 수정과 기술 스택 업그레이드가 기존 파싱 및 API 동작을 깨뜨리는지 자동으로 확인할 수 없다.

### 2. 개선 방법 정의

- 프로젝트·로그포맷·로그파일 모델의 기본 테스트를 추가한다.
- 프로젝트별 동적 테이블 생성과 조회에 대한 통합 테스트를 추가한다.
- 기준 데이터의 주요 필드와 집계 결과를 검증하는 파싱 테스트를 추가한다.
- 로그인, 프로젝트 생성, 파일 등록, 분석 요청의 핵심 API 테스트를 추가한다.
- 프런트엔드는 우선 빌드 성공과 핵심 화면 수동 시나리오를 기록한다.

### 3. 테스트 방법 및 데이터 확인

- 깨끗한 테스트 DB에서 전체 테스트를 실행한다.
- 테스트를 한 번 의도적으로 실패시켜 검증이 실제로 작동하는지 확인한다.
- 테스트 실행이 개발 DB와 업로드 원본을 변경하지 않는지 확인한다.

### 4. 결과 확인

- 핵심 파싱 및 API 테스트가 반복 실행된다.
- 테스트 전후 개발 DB의 데이터가 변하지 않는다.
- 이후 모든 작업에서 동일 테스트 명령을 사용할 수 있다.

### 단계 통과 조건

작업 1과 작업 2가 완료되기 전에는 Django, pandas, Vue 등의 주 버전을 변경하지 않는다.

# 2단계: 기술 현대화 전에 치명적 기능 위험 제거

## 작업 3. 임시 파일 및 대용량 명백 오류 수정

- 상태: 완료
- 선행조건: 작업 2
- 관련 상세 작업: 기능 개선 계획 작업 1, 작업 2

```text
담당자: Codex
시작일: 2026-08-11
완료일: 2026-08-11
관련 커밋/PR: 커밋 전
테스트 결과: PostgreSQL 격리 테스트 DB에서 11개 테스트 통과
              성공·실패 작업 디렉터리 정리, 5행/3청크 강제 분할,
              마지막 청크 나머지 행 및 마지막 개행 없는 파일 검증
백업 위치: Git 작업 트리(커밋 전)
발견된 추가 과제: 압축 파일의 형식·경로·크기 검증은 작업 10에서 수행
```

### 1. 개선 필요항목 정의

파싱 임시 CSV와 압축 해제 파일이 남을 수 있다. 대용량 분할 경로에는 `diff_hour` 인자 누락과 마지막 나머지 행 누락 가능성이 있다.

### 2. 개선 방법 정의

- 작업별 임시 디렉터리를 사용하고 `finally`에서 정리한다.
- 원본 업로드 파일은 삭제 대상에서 제외한다.
- 대용량 파서 호출 인자를 통일한다.
- 마지막 청크에 나머지 행을 포함한다.
- 이번 작업에서는 기존 pandas 및 `skiprows` 처리 구조를 유지한다.

### 3. 테스트 방법 및 데이터 확인

- 정상 처리와 강제 실패 후 임시 파일 존재 여부를 확인한다.
- 101행 파일을 여러 청크로 나누어 첫 행과 마지막 행을 확인한다.
- `diff_hour` 0, 양수 및 음수 조건을 확인한다.

### 4. 결과 확인

- 성공과 실패 모두 임시 파일이 남지 않는다.
- 원본 파일은 보존된다.
- 대용량 경로에서 인자 오류가 발생하지 않는다.
- 저장된 행의 중복과 마지막 행 누락이 없다.

## 작업 4. 처리 건수와 실패 행 확인 기능

- 상태: 완료
- 선행조건: 작업 3
- 관련 상세 작업: 기능 개선 계획 작업 3, 작업 4

```text
담당자: Codex
시작일: 2026-08-11
완료일: 2026-08-11
관련 커밋/PR: 커밋 전
테스트 결과: PostgreSQL 격리 테스트 DB에서 migration 0004 적용 및
              12개 테스트 통과. 비정상 5행 중 2행 저장·3행 거부,
              API 건수 불변조건과 거부 행 번호·오류 코드 검증 완료
백업 위치: Git 작업 트리(커밋 전)
발견된 추가 과제: reject 원문의 보관기간·마스킹·사용자 조회 API 정책 필요
                   개발 DB migration 적용은 배포 시 별도 수행 필요
```

### 1. 개선 필요항목 정의

포맷이 맞지 않는 행이 조용히 제외될 수 있고, API 성공만으로 원본 행과 저장 행의 일치 여부를 알 수 없다.

### 2. 개선 방법 정의

- `source_count`, `parsed_count`, `rejected_count`, `stored_count`를 계산한다.
- 실패 행의 원본 행 번호, 원문 및 오류 사유를 reject 결과로 보존한다.
- 결과를 API 응답과 구조화된 로그에 제공한다.
- 건수 불일치 또는 실패 행 존재 시 완전 성공과 구분한다.
- reject 데이터의 보관기간과 접근 권한을 정의한다.

### 3. 테스트 방법 및 데이터 확인

- 정상 95행과 비정상 5행이 포함된 파일을 분석한다.
- 빈 파일, 개행 없는 마지막 행, 잘못된 날짜 및 숫자 필드를 테스트한다.
- API 건수와 실제 DB `COUNT(*)`를 비교한다.

### 4. 결과 확인

- `source_count = parsed_count + rejected_count`가 성립한다.
- `stored_count = parsed_count`가 성립한다.
- 실패한 모든 행의 위치와 사유를 확인할 수 있다.
- 실패 행이 있는 작업은 완전 성공으로 표시되지 않는다.

- 선행조건: 작업 4

### 1. 개선 필요항목 정의

작은 압축 파일이 압축 상태로 파서에 전달될 수 있고 ZIP 내부 파일 검증이 부족하다. 같은 내용을 다른 이름으로 업로드하는 중복도 판별하기 어렵다.

### 2. 개선 방법 정의

- 원본 파일의 SHA-256을 스트리밍 계산한다.
- Gzip은 크기와 관계없이 signature를 확인해 스트림 처리한다.
- ZIP은 우선 검증된 단일 로그 파일만 허용한다.
- ZIP 경로 순회, 압축 해제 합산 크기 및 압축률을 제한한다.
- 다중 파일 ZIP 지원은 별도 후속 작업으로 둔다.

### 3. 테스트 방법 및 데이터 확인

- 일반 파일과 동일 내용의 GZ 및 ZIP 결과를 비교한다.
- 파일명만 다른 동일 파일과 한 줄이 다른 파일의 해시를 비교한다.
- 손상된 압축 파일, 경로 순회 ZIP 및 제한 초과 파일을 테스트한다.

### 4. 결과 확인

- 일반, GZ 및 허용 ZIP의 파싱 결과가 동일하다.
- 위험하거나 지원하지 않는 압축 파일이 명확한 사유로 거부된다.
- 동일 내용 파일을 식별하되 설정이 다른 재분석은 별도 작업으로 관리할 수 있다.

```text
담당자: Codex
시작일: 2026-08-12
완료일:
관련 커밋/PR: 커밋 전
테스트 결과: 순차 청크 파싱과 native COPY 적재, COPY 실패 보상 삭제를
             포함한 백엔드 회귀 테스트 17개 통과. COPY 파일 크기·처리시간·
             처리량 로그 계측 추가. 개발 서버·프런트 HTTP 200 확인.
발견된 추가 과제: 대용량 샘플 기준 메모리 지표와 포맷별 처리량 비교 필요.
```

### 1. 개선 필요항목 정의

현재 파일을 원문과 파싱 목적으로 반복해서 읽고, 임시 CSV를 쓴 후 다시 읽어 DB에 저장한다. `skiprows` 방식은 뒤쪽 청크일수록 앞부분을 반복 스캔한다.

### 2. 개선 방법 정의

- Apache 한 포맷에 순차 `chunksize` 처리를 먼저 도입한다.
- 한 번의 순회에서 원문과 파싱 필드를 생성한다.
- 청크 결과를 제한된 메모리 버퍼에서 PostgreSQL COPY로 전달한다.
- 기존 방식은 비교와 롤백을 위한 fallback으로 유지한다.
- Apache 완료 후 Nginx와 IIS를 각각 별도 커밋으로 확장한다.

### 3. 테스트 방법 및 데이터 확인

- 10만 행 이상 파일을 기존 방식과 신규 방식으로 처리한다.
- 전체 행, 주요 필드, 상태별 집계, 최초·최종 시각을 비교한다.
- 처리시간, 최대 메모리 및 임시 디스크 사용량을 측정한다.
- DB 연결 실패 후 재처리 결과를 확인한다.

### 4. 결과 확인

- 신규 처리 결과가 기준 결과와 일치한다.
- 파일 크기 전체에 비례하는 메모리를 사용하지 않는다.
- 중간 CSV가 생성되지 않는다.
- 변경 전후 성능 측정값이 기록돼 있다.

## 작업 12. 포맷별 파서 분리와 등록 시 사전 검증

- 상태: 진행 중 (포맷별 parser 클래스 레지스트리·사전 검증 API 완료)
- 선행조건: 작업 11
- 관련 상세 작업: 기능 개선 계획 작업 12, 작업 13

### 1. 개선 필요항목 정의

여러 포맷의 파싱 로직이 큰 ViewSet에 혼재해 변경 영향 범위가 크다. 포맷 오류도 대용량 파일을 분석할 때 처음 발견된다.

### 2. 개선 방법 정의

- 동작 변경 없이 파싱 로직을 서비스와 포맷별 클래스로 이동한다.
- Apache, Nginx, IIS, App 파서를 한 번에 하나씩 분리한다.
- `validate_format`, `parse_chunk`, `normalize` 공통 계약을 적용한다.
- 포맷 등록 시 샘플 1~10행을 파싱해 추출 결과를 미리 보여준다.
- 기존 포맷은 검증 상태를 표시하고 즉시 삭제하지 않는다.

### 3. 테스트 방법 및 데이터 확인

- 분리 전후 기준 로그의 모든 저장 컬럼을 비교한다.
- 공백, 따옴표, 긴 User-Agent 및 누락 필드가 포함된 샘플을 검증한다.
- 지원하지 않는 `format_kind`와 잘못된 포맷을 확인한다.

### 4. 결과 확인

- ViewSet이 파싱 구현 세부사항을 직접 포함하지 않는다.
- 포맷별 테스트를 독립적으로 실행할 수 있다.
- 사용자가 대용량 분석 전에 포맷 오류를 확인할 수 있다.

# 5단계: 저장 모델 전환 검증

## 작업 13. V2 데이터 모델과 조회 인덱스 병행 검증

- 상태: 완료 (V2 병행 적재·건수·상태·바이트 집계 및 처리 시간 비교 연결)
- 선행조건: 작업 12
- 관련 상세 작업: 기능 개선 계획 작업 14, 작업 15

### 1. 개선 필요항목 정의

현재 동적 테이블은 날짜, 상태, UUID 등을 문자열로 저장하고 주요 조회 인덱스가 없다. 긴 문자열 제한과 시간대 손실도 발생할 수 있다.

### 2. 개선 방법 정의

- 기존 테이블을 바로 변경하지 않고 정적 `log_detail_v2` 모델을 추가한다.
- 시각은 `timestamptz`, 상태는 `smallint`, 크기와 응답시간은 `bigint`, 원문은 `text`, 로그파일은 UUID 외래키로 저장한다.
- 응답시간 미측정 값은 추정하지 않고 `NULL`로 저장한다.
- 기존 동적 테이블과 V2에 병행 적재한다.
- 실제 쿼리의 `EXPLAIN ANALYZE`를 보고 복합 인덱스를 적용한다.

### 3. 테스트 방법 및 데이터 확인

- 같은 로그를 기존 테이블과 V2에 병행 저장한다.
- 행 수, 상태별 집계, 기간 조회, URI 통계 및 시간대 정렬을 비교한다.
- 긴 URI와 User-Agent를 확인한다.
- 인덱스 전후 조회시간, 적재시간 및 저장공간을 측정한다.

### 4. 결과 확인

- V2 결과와 기존 정상 결과의 차이를 설명할 수 있다.
- 긴 문자열 때문에 전체 적재가 실패하지 않는다.
- 시간대와 미측정 응답시간이 정확하게 표현된다.
- 인덱스의 조회 개선과 적재 비용이 수치로 기록된다.

### 롤백 기준

병행 저장을 끄면 기존 동적 테이블만으로 즉시 운영할 수 있어야 한다.

## 작업 14. 동적 테이블 전환 및 최종 운영 승인

- 상태: 진행 중 (readiness·백필·10,000행 AS-IS/TO-BE 성능 비교 완료)
- 선행조건: 작업 13의 충분한 병행 검증
- 관련 상세 작업: 기능 개선 계획 작업 16, 기술 스택 계획 5단계와 9단계

### 1. 개선 필요항목 정의

프로젝트별 동적 테이블은 스키마, 인덱스, 외래키 및 migration 관리가 어렵고 오래된 동적 모델 패키지에 핵심 기능이 종속된다. 그러나 즉시 제거하면 기존 데이터와 조회 기능의 대규모 회귀 위험이 있다.

### 2. 개선 방법 정의

- V2 병행 운영 기간과 허용 오차를 먼저 정의한다.
- 데이터 규모에 따라 월 단위 또는 프로젝트 해시 파티셔닝을 검증한다.
- 읽기 API를 V2로 전환하되 기능 플래그로 기존 API에 복귀할 수 있게 한다.
- 기존 데이터 이관은 프로젝트 또는 기간 단위 배치로 나눈다.
- 최종 승인 전 백업, 복구, 성능 및 삭제 정책을 점검한다.
- 검증 완료 후 별도 승인 작업에서 `django-dynamic-model` 의존성을 제거한다.

### 3. 테스트 방법 및 데이터 확인

- 기존 DB 복사본으로 전체 이관을 반복 실행한다.
- 프로젝트별 행 수와 통계를 양쪽 구조에서 비교한다.
- 이관 중단 후 재시작, 중복 방지 및 롤백을 테스트한다.
- 기간 조회, 통계, 프로젝트 삭제, 백업 및 복구 성능을 확인한다.
- 핵심 사용자 흐름의 최종 E2E 테스트를 실행한다.

### 4. 결과 확인

- 모든 이관 대상의 건수와 검증 결과가 기록돼 있다.
- V2 API가 운영 성능 기준을 만족한다.
- 기능 플래그 또는 백업으로 기존 구조에 복귀할 수 있다.
- 운영 승인 후에만 동적 테이블 생성과 패키지 의존성을 제거한다.
