# ELAO 스택 현대화 작업 절차

## 1. 목적

이 문서는 ELAO 프로젝트를 현재 동작을 최대한 보존하면서 현대적인 지원 버전으로 전환하기 위한 Codex 작업 절차를 정의한다.

핵심 원칙은 다음과 같다.

- 현대화 전에 현재 동작을 자동 테스트로 고정한다.
- 한 번에 전면 재작성하지 않고 작은 단계로 변경한다.
- 각 단계는 테스트, 빌드, 스모크 테스트를 모두 통과해야 완료된다.
- 검증에 실패하면 다음 단계로 진행하지 않는다.
- 운영 데이터와 기존 동적 테이블은 검증 완료 전까지 삭제하지 않는다.
- 실패한 검사나 경고를 임의로 비활성화하지 않는다.

## 2. 목표 기술 스택

| 영역 | 현재 | 목표 |
|---|---|---|
| Python | 미지정 | Python 3.12 |
| 백엔드 | Django 3.0.4 | Django 5.2 LTS |
| API | DRF 3.11 | Django 5.2 호환 DRF |
| 인증 | django-rest-auth | 지원되는 인증 구성 |
| 데이터베이스 | PostgreSQL, 버전 미지정 | PostgreSQL 16 또는 17 |
| DB 드라이버 | psycopg2 2.8.5 | psycopg 3 |
| 프론트엔드 | Vue 2.6 | Vue 3 |
| 빌드 | Vue CLI 3 | Vite |
| 상태 관리 | Vuex 3 | Pinia |
| 스타일 | node-sass | Dart Sass |
| 차트 | Chart.js 2 | Chart.js 4 |
| 테스트 | 실질적으로 없음 | pytest, Vitest, Playwright |
| 실행 환경 | 수동 구성 | Docker Compose 및 CI |

## 3. 자동화 및 승인 원칙

### Codex가 자율적으로 수행할 작업

- 저장소와 실행 구조 조사
- 코드, 설정, 테스트 및 문서 수정
- 개발용 의존성 설치
- 로컬 Docker 이미지와 컨테이너 생성
- 테스트 전용 데이터베이스 생성 및 초기화
- 정적 분석, 테스트, 빌드 및 취약점 검사
- 테스트 DB 대상 마이그레이션 생성과 검증
- 단계별 작업 보고서 작성

### 사람의 승인이 필요한 작업

- 운영 데이터베이스 접근 또는 변경
- 기존 데이터나 동적 테이블 삭제
- 실제 비밀키와 운영 자격 증명 사용
- 외부 서버 또는 클라우드 배포
- DNS, 방화벽 및 운영 인프라 변경
- 되돌리기 어려운 Git 작업

## 4. 공통 작업 루프

모든 단계에서 Codex는 아래 순서를 반복한다.

1. 관련 코드와 의존성을 조사한다.
2. 변경 전 동작을 테스트로 표현한다.
3. 한 가지 목적의 작은 변경을 수행한다.
4. 정적 검사와 단위 테스트를 실행한다.
5. 백엔드 및 프론트엔드 빌드를 실행한다.
6. Docker 통합 환경에서 API 스모크 테스트를 실행한다.
7. 실패하면 원인을 수정하고 검증을 반복한다.
8. 통과한 변경과 남은 위험을 문서화한다.

## 5. 단계별 절차

### 0단계: 기준선과 재현 가능한 실행 환경 구축

#### 작업

- 현재 브랜치, 변경 파일 및 저장소 상태를 기록한다.
- Python과 Node.js 버전을 고정한다.
- `.env.example`을 작성하고 비밀값을 코드 밖으로 이동한다.
- PostgreSQL, 백엔드, 프론트엔드를 포함하는 Docker Compose 환경을 작성한다.
- 개발·테스트·운영 의존성을 구분한다.
- 백엔드와 프론트엔드의 실행 명령을 문서화한다.
- CI에서 설치, 검사, 테스트, 빌드를 실행하도록 구성한다.
- 샘플 데이터만 사용하는 초기화 절차를 작성한다.

#### 완료 조건

- `docker compose up --build`로 전체 개발 환경이 실행된다.
- 빈 테스트 DB에서 마이그레이션을 적용할 수 있다.
- 비밀정보 없이 `.env.example`만으로 필요한 설정을 알 수 있다.
- 기존 운영 데이터에 접근하지 않는다.

### 1단계: 현재 동작을 회귀 테스트로 고정

#### 백엔드 테스트

- 모델 및 serializer 테스트
- 회원가입, 로그인, 로그아웃 및 권한 테스트
- 프로젝트 CRUD 테스트
- 로그 형식과 메트릭 CRUD 테스트
- 로그 파일 업로드 및 파싱 테스트
- 검색, 통계 및 차트 API 계약 테스트
- 동적 로그 모델 생성·조회·삭제 테스트
- 잘못된 입력과 권한 오류 테스트

#### 프론트엔드 및 E2E 테스트

- 주요 Vue 컴포넌트 테스트
- API 오류와 로딩 상태 테스트
- 로그인부터 프로젝트 생성까지의 브라우저 테스트
- 대표 로그 업로드, 분석, 검색 및 통계 조회 테스트
- 프로젝트 삭제 흐름 테스트

#### 완료 조건

- 대표 사용자 흐름이 자동 테스트로 검증된다.
- 대표 로그 파일의 분석 결과가 기준 데이터로 고정된다.
- 모든 테스트가 격리된 테스트 DB에서 반복 실행된다.
- 테스트 실패 없이 다음 단계로 진행할 수 있다.

### 2단계: 보안과 환경설정 정상화

#### 작업

- `SECRET_KEY`, DB 암호, 호스트 및 미디어 경로를 환경변수로 이동한다.
- 운영 환경에서 `DEBUG=False`를 강제한다.
- CORS 허용 출처를 명시적으로 제한한다.
- 모든 데이터 API에 기본 인증 정책을 적용한다.
- 프로젝트 및 로그에 객체 단위 소유권 검사를 적용한다.
- 사용자 serializer에서 허용 필드만 명시한다.
- 비밀번호 생성과 변경에 `set_password()`를 사용한다.
- 업로드 파일 크기, 파일명, 확장자 및 저장 경로를 검증한다.
- 동적 테이블 생성·삭제 작업에 관리자 권한과 입력 검증을 적용한다.
- 프론트엔드 인증 헤더와 로그아웃 시 토큰 제거를 중앙화한다.
- 로그에서 토큰, 암호 및 개인정보를 제거한다.

#### 완료 조건

- 익명 사용자는 보호된 데이터 API에 접근할 수 없다.
- 일반 사용자는 다른 사용자의 프로젝트를 변경할 수 없다.
- 저장소에 실제 비밀값이 존재하지 않는다.
- `python manage.py check --deploy`가 통과한다.
- 보안 회귀 테스트가 통과한다.

### 3단계: 백엔드 의존성과 코드 구조 정리

#### 작업

- 중복된 `django-rest-framework` 패키지를 제거한다.
- PyPI와 Git으로 중복 설치되는 `django-dynamic-model`을 정리한다.
- HTTP Git 의존성과 editable 운영 의존성을 제거한다.
- 미사용 패키지와 import를 제거한다.
- 재현 가능한 의존성 잠금 파일을 생성한다.
- 거대한 `views.py`를 API, serializer, service 및 task 계층으로 분리한다.
- 파싱, 통계, 파일 처리를 독립적인 서비스 함수로 이동한다.

#### 완료 조건

- 깨끗한 환경에서 의존성이 동일하게 설치된다.
- 전체 회귀 테스트 결과가 변경 전과 일치한다.
- API 응답 계약이 유지된다.

### 4단계: Django 점진적 업그레이드

다음 순서로 한 버전 구간씩 진행한다.

```text
Django 3.0 → 3.2 → 4.2 → 5.2 LTS
```

#### 각 구간의 작업

1. 대상 Django와 호환되는 패키지 버전을 결정한다.
2. deprecation 경고를 수집하고 원인을 수정한다.
3. URL, 설정, middleware, ORM 및 serializer 호환성을 수정한다.
4. 마이그레이션의 변경 내용을 검토한다.
5. 전체 테스트와 API 스모크 테스트를 실행한다.
6. Docker 이미지를 새로 빌드한다.
7. 모든 검증이 통과한 경우에만 다음 구간으로 이동한다.

#### 완료 조건

- Django 5.2 LTS에서 전체 테스트가 통과한다.
- 생성된 마이그레이션에 예상하지 못한 데이터 삭제가 없다.
- 경고를 숨기지 않고 업그레이드 관련 경고를 해결한다.

### 5단계: 동적 로그 테이블 구조 개선

현재의 프로젝트별 동적 테이블은 최신 Django 호환성과 운영 안정성에 가장 큰 위험 요소다.

#### 목표 구조

- 공통 `LogDetail` 테이블
- 프로젝트 및 로그 파일 외래키
- 날짜 또는 프로젝트 기준 PostgreSQL 파티셔닝
- 검색 조건에 맞춘 복합 인덱스
- 확장 필드가 필요하면 제한된 JSONB 사용

#### 마이그레이션 작업

- 기존 동적 테이블을 탐색하는 관리 명령을 작성한다.
- 새 스키마와 인덱스를 생성한다.
- 데이터를 배치 단위로 복사한다.
- 원본과 대상의 건수, 범위 및 체크섬을 비교한다.
- 읽기 경로를 기능 플래그로 전환한다.
- 회귀 테스트와 성능 테스트를 실행한다.
- 검증 기간 동안 원본 테이블을 읽기 전용으로 보존한다.

#### 완료 조건

- 데이터 건수와 검증 값이 원본과 일치한다.
- 대표 검색 및 통계 결과가 기존 결과와 일치한다.
- 성능이 허용 기준을 충족한다.
- 원본 삭제는 별도의 사람 승인을 받기 전까지 수행하지 않는다.

### 6단계: 로그 분석 작업 비동기화

#### 목표 구조

```text
Vue → Django API → Redis → Worker → PostgreSQL
```

#### 작업

- 파일 업로드와 로그 분석 요청을 분리한다.
- Celery 또는 Dramatiq 기반 작업 큐를 추가한다.
- 작업 상태, 진행률 및 오류 모델을 추가한다.
- 재시도, 제한시간, 취소 및 중복 방지 정책을 구현한다.
- 분석 작업을 멱등하게 만든다.
- 프론트엔드가 작업 ID로 진행 상태를 조회하도록 변경한다.

#### 완료 조건

- 대용량 파일 처리 중 API 요청이 장시간 점유되지 않는다.
- 실패한 작업을 안전하게 재시도할 수 있다.
- 같은 파일의 중복 실행으로 결과가 중복 저장되지 않는다.

### 7단계: 프론트엔드 점진적 현대화

다음 순서로 진행한다.

1. `node-sass`를 Dart Sass로 교체한다.
2. Vue CLI 환경에서 기존 프로덕션 빌드를 복구한다.
3. Vue 2.6을 Vue 2.7로 올린다.
4. 핵심 컴포넌트 테스트를 보강한다.
5. `lego-component`의 Vue 3 호환성을 조사한다.
6. 필요한 경우 호환 래퍼를 만든다.
7. Vue 3로 전환한다.
8. Vue Router 4로 전환한다.
9. Vue CLI를 Vite로 교체한다.
10. Vuex를 Pinia로 점진 교체한다.
11. Chart.js 4로 업그레이드한다.
12. Moment.js를 표준 `Intl`, date-fns 또는 dayjs로 교체한다.

#### 완료 조건

- Vite 프로덕션 빌드가 성공한다.
- 핵심 화면과 E2E 테스트가 통과한다.
- Vue 2 및 node-sass 런타임 의존성이 제거된다.
- 기존 화면의 주요 기능과 시각적 결과가 유지된다.

### 8단계: API 클라이언트와 계약 정리

#### 작업

- 프론트엔드의 Axios 설정을 단일 API 클라이언트로 통합한다.
- 인증, 타임아웃, 취소 및 오류 처리를 interceptor에서 관리한다.
- 기능별 API 모듈을 작성한다.
- 백엔드 OpenAPI 스키마를 생성한다.
- 프론트엔드 API 타입을 자동 생성한다.
- 오류 응답과 페이지네이션 형식을 통일한다.
- 필요 시 Vue 파일을 TypeScript로 점진 변환한다.

#### 완료 조건

- 화면 컴포넌트가 URL과 인증 헤더를 직접 조립하지 않는다.
- API 계약 변경이 CI에서 탐지된다.
- 전체 통합 테스트가 통과한다.

### 9단계: 최종 운영 검증

#### 필수 검사

- 빈 DB에서 설치 및 마이그레이션
- 관리자 계정과 테스트 사용자 생성
- 로그인과 권한 검사
- 대표 로그 업로드 및 분석 결과 비교
- 백엔드 전체 테스트
- 프론트엔드 단위 테스트
- 브라우저 E2E 테스트
- 프론트엔드 프로덕션 빌드
- Django 배포 검사
- 의존성 취약점 및 라이선스 검사
- 백업과 복원 테스트
- 데이터 마이그레이션 리허설
- 성능 기준 비교
- 롤백 절차 검증

#### 최종 승인 기준

| 검사 | 기준 |
|---|---|
| 백엔드 테스트 | 100% 통과 |
| 프론트엔드 테스트 | 100% 통과 |
| 핵심 E2E | 100% 통과 |
| Django deploy check | 통과 |
| 프로덕션 빌드 | 통과 |
| 대표 로그 분석 결과 | 기존 기준값과 일치 |
| 고위험 보안 항목 | 0개 |
| DB 마이그레이션 및 롤백 | 검증 완료 |

## 6. Codex 작업 요청 템플릿

### 최초 기준선 구축

```text
plans/STACK_MODERNIZATION_PLAN.md의 0~1단계를 수행해줘.

저장소와 현재 실행 구조를 먼저 조사하고, Docker Compose 기반 재현 환경과
핵심 회귀 테스트를 구축해. 실제 프로덕션 코드는 테스트 실행에 필요한
최소 범위만 수정해.

완료 조건:
- docker compose up --build 성공
- 전체 자동 테스트 성공
- 대표 사용자 흐름 E2E 성공
- 기존 데이터와 동적 테이블을 삭제하지 않음
- 실패한 검증을 숨기거나 건너뛰지 않음

운영 데이터 접근, 외부 배포, 비밀키 사용 및 데이터 삭제만 내 승인을 받아라.
그 외 범위 내 작업은 스스로 조사하고 진행해.
```

### 보안 및 의존성 정리

```text
plans/STACK_MODERNIZATION_PLAN.md의 2~3단계를 수행해줘.
인증과 보안 문제를 수정하고 백엔드 의존성을 정리해.
각 변경 후 테스트와 빌드를 실행하고, 검증 실패 시 다음 단계로 넘어가지 마.
운영 데이터나 기존 동적 테이블은 변경하지 마.
```

### Django 업그레이드

```text
plans/STACK_MODERNIZATION_PLAN.md의 Django 업그레이드를 한 구간만 진행해줘.
현재 버전에서 다음 목표 버전까지만 올리고, 호환성 문제와 deprecation 경고를
수정해. 전체 테스트, 마이그레이션 검사, Docker 빌드 및 API 스모크 테스트가
모두 통과해야 완료로 판단해. 데이터 삭제는 수행하지 마.
```

### 프론트엔드 업그레이드

```text
plans/STACK_MODERNIZATION_PLAN.md의 프론트엔드 현대화를 다음 미완료 항목 하나까지만
진행해줘. 변경 전 컴포넌트와 E2E 테스트를 보강하고, 프로덕션 빌드 및 전체
회귀 테스트가 통과하도록 수정해. lego-component 호환성 문제가 발생하면
기존 화면을 제거하지 말고 호환 래퍼 또는 점진적 대체안을 적용해.
```

## 7. 단계별 결과 보고 형식

각 작업 완료 시 Codex는 다음 항목을 보고한다.

1. 완료한 단계와 변경 목적
2. 변경한 주요 파일
3. 실행한 검사와 결과
4. 해결한 오류와 보안 문제
5. 남아 있는 위험과 기술 부채
6. 데이터 및 API 호환성 영향
7. 롤백 방법
8. 다음 권장 단계

## 8. 금지 사항

- 테스트 없이 대규모 프레임워크 업그레이드를 수행하지 않는다.
- 여러 주요 버전 업그레이드를 하나의 검증 단계로 합치지 않는다.
- 운영 DB를 개발 및 테스트 DB로 사용하지 않는다.
- 원본 동적 테이블을 자동 삭제하지 않는다.
- 테스트 실패, 보안 경고 또는 deprecation 경고를 단순히 비활성화하지 않는다.
- 실제 자격 증명을 저장소에 추가하지 않는다.
- 기존 사용자 변경사항을 임의로 되돌리지 않는다.
- 전체 기능을 한 번에 재작성하지 않는다.
